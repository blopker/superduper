# SuperDuper V2 plan

Status: proposed implementation plan

This document turns the current feature baseline in
[`docs/FEATURE_SET.md`](docs/FEATURE_SET.md) into an implementation plan for
SuperDuper V2. V2 keeps the product's identity and bike-control capabilities,
but replaces its application architecture, persistence, and primary workflows.

The plan is intentionally specific enough to guide implementation and testing.
Items labeled as experiments must be proven before they become release
commitments.

## Outcome

V2 will be a local-first Android and iOS app that:

- Finds and controls compatible SUPER73 bikes over BLE.
- Saves and switches among multiple bikes.
- Automatically prepares one active bike when the app opens.
- Controls Light, Mode, and Assist with correct US and EU wire encoding.
- Separates values reported by the bike from values the rider wants to keep.
- Persists bike metadata and desired settings in SQLite.
- Imports existing on-device SuperDuper data without deleting its source files.
- Uses Signals for explicit, fine-grained application and session state.
- Preserves the dark, bold, gradient-driven visual identity while simplifying
  navigation and interaction.
- Works without an account, backend, analytics service, or network connection.

Android background enforcement is a gated experiment. It will ship only if the
new implementation meets the lifecycle, reliability, battery, and policy gates
defined below. Foreground setting enforcement remains part of V2 regardless of
that experiment's outcome.

## Core value: open and ride

Until background enforcement is proven, the critical V2 workflow is:

1. The rider turns on their bike and opens SuperDuper.
2. SuperDuper identifies the persisted active bike without requiring a tap.
3. It immediately connects by the saved BLE identity while Home remains
   visible; it does not perform a discovery scan first.
4. It discovers and validates the required services.
5. It reads the bike's current configuration.
6. It merges the current unlocked values with the rider's persisted locked
   values.
7. If the merged configuration differs, it sends one complete configuration
   write.
8. It reads again when needed to confirm the result.
9. It reports `Ready to ride` only after the bike is connected and all locked
   settings are confirmed.

There must be no artificial scan wait, fixed startup delay, or route navigation
in this path. If the bike is off or unavailable, Home explains that and retries
while the app is in the foreground. Opening the control screen is optional.

This zero-tap active-bike synchronization is the primary product value and has
priority over visual polish, secondary settings, and background experiments.
Measure foreground-visible-to-ready latency on real hardware and treat material
regressions as release blockers.

## Product principles

### Local first

Bike identifiers, names, colors, regions, desired settings, and lock choices
remain on the device. V2 will not add accounts, cloud sync, telemetry,
advertising, or a SuperDuper backend.

### Honest state

The interface must distinguish:

- What the bike most recently reported.
- What the rider most recently selected.
- Which values the app is currently enforcing.
- Whether the app is able to communicate with the bike.

Disconnected, stale, pending, and failed state must not look connected or
confirmed.

### One obvious workflow

Discovery is part of adding a bike, not a permanent section of the home screen.
Connecting, disconnecting, and forgetting are separate actions. A saved bike is
created at a clear confirmation point, not as a side effect of a later BLE read
or write.

### Reliability before breadth

V2 will not add ride tracking, maps, telemetry, firmware updates, automation
schedules, cloud features, or new bike capabilities. The first release is
successful when the existing controls and persistence are predictable and easy
to use.

### Small architecture

The app should have clear boundaries without introducing a framework for every
boundary. Signals is state management, Drift is persistence, constructors are
dependency injection, and the Flutter navigation APIs are sufficient for the
initial route graph.

## Proposed product decisions

These decisions simplify behavior while preserving the useful feature set:

- The app always opens to Home. It does not automatically navigate into the
  active bike's control screen.
- Exactly one saved bike is active whenever at least one bike exists.
- The first bike a user confirms becomes active automatically.
- A user can make any other saved bike active from Home or Bike Settings.
- Opening the app automatically starts an app-scoped session for the active bike
  and synchronizes its locked settings without another tap.
- Home lists saved bikes and has one primary `Add bike` action.
- Scanning begins only inside the Add Bike flow.
- Only one bike session is active at a time. Selecting a non-active bike creates
  a temporary session without changing the persisted active bike. Making a bike
  active switches both the persisted choice and current session.
- A newly discovered bike is saved only after the user confirms its name and
  region.
- Light uses a direct on/off control.
- Mode exposes four direct choices instead of requiring repeated taps to cycle.
- Assist exposes five direct choices instead of requiring repeated taps to
  cycle.
- The padlock interaction becomes a labeled `Keep this setting` control.
- Live controls are disabled while disconnected. Offline presets are not part
  of the first V2 release.
- `Disconnect` ends the current session but retains the saved bike.
- Manually disconnecting pauses automatic reconnection for the current app
  session; the next app launch resumes active-bike synchronization.
- `Forget bike` closes the session, removes the local record, and returns Home.
- Forgetting the active bike promotes the earliest remaining saved bike. If no
  bikes remain, there is no active bike.
- The BLE device identifier is available in bike details and diagnostics, but
  is not primary card text.
- A previous Background Lock preference is imported but never starts background
  work until the rider explicitly consents to the V2 behavior.

These are product decisions, not incidental implementation behavior. If one is
changed, its acceptance tests and relevant workflow must change with it.

## Experience design

### Route map

```text
Startup
  ├─ Migration recovery, only when installed data cannot be imported
  └─ Home
       ├─ Active bike setup: connecting → applying settings → ready to ride
       ├─ Add Bike
       │    ├─ Permission guidance
       │    ├─ Discovery
       │    ├─ Connection and verification
       │    └─ Confirm bike
       └─ Bike Control
            ├─ Bike Settings
            ├─ Connection help
            └─ Background enforcement setup, Android only if supported
```

### Startup

Startup performs only work required to render trustworthy local state:

1. Open or create the SQLite database.
2. Run schema migrations.
3. Check for installed-app JSON data and import it when needed.
4. Construct application services and Signals controllers.
5. Render Home.
6. Start active-bike synchronization as soon as local state and the required
   platform capability are ready.

A fresh install with no saved bike can reach Home without granting hardware
access. When an active bike exists, startup checks the required Bluetooth
capability immediately. Previously granted access allows zero-tap connection;
missing or revoked access produces one focused recovery action instead of an
empty or silently disconnected state.

The normal startup UI has three explicit states:

- Initializing local data.
- Migration recovery required.
- Ready.

An initialization failure includes a retry action and a locally useful error
message. It must not silently appear as an empty bike library.

### Home

Home presents:

- The SuperDuper identity and dark visual system.
- Saved bikes in stable saved order.
- Each bike's name, color, active status, and a concise
  connection/availability state.
- An `Add bike` primary action.
- An empty state that explains how to turn the bike on and add it.
- Active-bike progress that moves through connecting, applying locked settings,
  and `Ready to ride`.

Home does not start an indefinite scan. It may show the most recent locally
known state, but stale state must be labeled and must not imply a live
connection.

The app-scoped active-bike session does not depend on Bike Control being open.
Selecting the active bike opens its existing session. Selecting a non-active
bike closes or suspends the current runtime session and opens a temporary
session for the selected bike; the persisted active designation does not change
unless the user chooses `Make active`.

### Add Bike

Add Bike is a guided, cancellable workflow:

1. Explain why Bluetooth access is needed.
2. Request only the permissions required by the current OS version.
3. Show actionable adapter-off, denied, permanently-denied, restricted, and
   unavailable states.
4. Start a filtered scan for `SUPER73` and `S73 FTEX` advertisements.
5. Show discovered devices without duplicating saved bikes.
6. Let the user select one result.
7. Connect, discover services, and read the bike configuration.
8. Infer region from the wire mode and ask the user to confirm it.
9. Suggest the deterministic friendly name and allow editing.
10. Confirm and save the bike in one database transaction.
11. If it is the first saved bike, make it active in that transaction.
12. Open Bike Control with the verified session.

Scan results are ephemeral. Cancelling the flow does not create a saved bike.
Connection or protocol incompatibility is shown before confirmation and offers
retry, choose another bike, and cancel actions.

### Bike Control

Bike Control has four conceptual sections:

1. Bike identity and connection state.
2. Light, Mode, and Assist controls.
3. `Keep this setting` choices for each control.
4. Help and bike settings.

The connection component handles:

- Connecting.
- Connected.
- Reconnecting, including attempt status.
- Disconnected with a manual retry.
- Bluetooth disabled.
- Permission unavailable.
- Unsupported GATT shape.
- Read or write failure.

The control display uses the observed bike value when connected. A pending
write is visible until the bike confirms the resulting state. On failure, the
control returns to the last confirmed value and explains what happened.

Changing a control sends the complete Light, Assist, and Mode payload required
by the bike protocol. Commands are serialized so reads and writes cannot race.

### Setting enforcement

Each control has an independent `Keep this setting` choice.

When the user enables it:

1. The currently confirmed value becomes the desired value.
2. The desired value and enabled choice are saved transactionally.
3. Future authoritative reads are compared with that desired value.
4. A mismatch is corrected with one complete configuration write.
5. The app reads again to confirm the correction.

Unlocked settings follow the bike and do not trigger corrective writes.
Observed values are session state, not persistent desired state.

Foreground enforcement runs whenever the app-scoped runtime bike session is
active. The active bike's session begins at startup; it is not tied to the
control route. Without proven background support, enforcement is guaranteed
only while the app is foreground-active. The interface must state that limit
and resynchronize on the next launch.

### Bike Settings

Bike Settings allows the user to:

- Change the required display name.
- Change or confirm US/EU mode interpretation.
- Choose a named bike color.
- Make this the active auto-connect bike.
- View the BLE device identifier and local diagnostics.
- Disconnect the active session.
- Forget the bike through a destructive confirmation flow.

Changing the region does not immediately change the bike's current mode. The
next explicit mode command uses the newly selected encoding. If this could
produce an unexpected legal mode, the UI warns before saving the region.

Forgetting is atomic from the user's perspective: stop enforcement, disconnect,
dispose the session, delete the database record, and return Home. A disposed
session cannot recreate the record. If it was active, the same transaction
selects the earliest remaining bike as active; the session coordinator then
starts that bike unless automatic connection was manually paused.

### Help and recovery

Common recovery guidance should exist in the app for:

- Bluetooth off.
- Permission denial and opening system settings.
- Bike not advertising.
- Another app already connected to the bike.
- Unsupported firmware or missing GATT services.
- Repeated connection failure.

External FAQ and Getting Started links remain available, but they are not a
substitute for actionable local errors.

### Visual system and accessibility

Keep:

- Black surfaces.
- Bold, compact typography.
- Strong named gradients as bike identity.
- Large, card-like controls.

Improve:

- Contrast in inactive and disconnected states.
- Dynamic type and text-scale behavior.
- Screen-reader names, values, and actions.
- Minimum touch-target sizes.
- Focus order and keyboard navigation where supported.
- Portrait, landscape, and compact-width layout behavior.
- Status communication that never relies on color alone.
- Reduced-motion behavior for animated connection and scan states.

Colors are persisted by stable string key, not list position, so the palette can
be reordered without changing a saved bike's appearance.

## Technical direction

### Toolchain

- Pin one current stable Flutter SDK for local development and CI.
- Set the Dart language floor to at least 3.10.
- Keep the app on the stable Flutter channel.
- Record the exact Flutter version in the repository and release artifacts.
- Enable strict analysis and treat analyzer warnings as CI failures.
- Keep generated Drift files excluded from hand editing and normal lint noise.

Use modern Dart where it clarifies the domain:

- Sealed types and exhaustive switch expressions for lifecycle and error state.
- Object and record patterns for decoding and state handling.
- Enhanced enums for region and mode.
- Records for short-lived internal return values, not persisted entities.
- Null-aware collection elements.
- Dot shorthand where the context remains obvious.
- `final` classes and immutable domain values by default.

Avoid adding code generation for domain models initially. Drift's database code
generation is sufficient unless handwritten domain value semantics become a
meaningful burden.

### Dependencies

Planned core dependencies:

- `signals` for application and session state.
- `drift` and `drift_flutter` for SQLite persistence.
- `flutter_blue_plus` behind a SuperDuper-owned BLE adapter.
- `permission_handler` behind a platform-permission adapter.
- `url_launcher` for explicit external help actions.
- A structured logger with production-safe redaction.

Planned development dependencies:

- `drift_dev` and `build_runner`.
- Current Flutter lints plus stricter project rules.
- `signals_lint` if it supports the pinned Signals and analyzer versions.

Remove when their replacements are complete:

- Riverpod and Riverpod generation.
- JSON model generation used only by the installed-data format.
- Flutter Form Builder for the small settings form.
- `flutter_foreground_task` unless the background experiment proves that it is
  the correct execution host.

Do not add a routing, service-locator, or general architecture package without
a concrete requirement.

### Application boundaries

```text
Flutter views
    │ read readonly signals / invoke commands
    ▼
Feature controllers
    │
    ├─ Bike repository ─────────────── Drift / SQLite
    │
    ├─ Discovery controller ────────── BLE adapter
    │
    └─ Active-bike coordinator
         └─ Bike session ───────────── BLE transport + protocol codec
                                           │
                                           └─ Optional Android background adapter
```

Views do not call Drift, Flutter Blue Plus, permission plugins, or foreground
plugins directly.

Repositories and platform adapters are passed through constructors. An
app-owned `AppServices` object is exposed through one inherited scope at the
Flutter root. Tests construct controllers with in-memory repositories and fake
transports.

## State management with Signals

### Ownership

| State | Owner | Source of truth | Lifetime |
| --- | --- | --- | --- |
| Startup and import status | Startup controller | Database/import result | App startup |
| Saved bike list | Bike repository stream signal | SQLite | App |
| Active bike identity | Settings repository signal | SQLite | Permanent |
| Runtime selected bike | Active-bike coordinator | Active choice or explicit temporary selection | App session |
| Discovery status/results | Add Bike controller | BLE scan | Add Bike route |
| Permission and adapter state | Relevant feature controller | Platform APIs | Feature route |
| Connection state | Bike session | BLE transport | Runtime session |
| Observed bike config | Bike session | Latest validated BLE frame | Connection |
| Pending command | Bike session | Serialized command queue | Command |
| Desired config and lock choices | Repository-backed signal | SQLite | Permanent |
| Effective enforced config | Computed signal | Observed + desired + locks | Runtime session |
| Ride readiness | Computed signal | Connection + confirmation + enforcement | Runtime session |
| Background runtime status | Background adapter | Android service | Service session |

### Controllers

`StartupController` owns database initialization and installed-data import.

`HomeController` exposes a read-only signal backed by the Drift bike query and
commands for selecting a bike, making a bike active, and starting Add Bike. It
also exposes the active bike's app-scoped synchronization progress.

`AddBikeController` owns permission, adapter, scan, candidate connection, and
confirmation state. Disposing the controller stops scanning and disconnects an
unconfirmed candidate.

`ActiveBikeCoordinator` observes the persisted active bike after startup. It
starts the one allowed runtime session automatically, supports temporary manual
selection of a different bike, prevents route disposal from stopping active
synchronization, and honors an explicit manual-disconnect pause for the rest of
the app session.

`BikeSession` owns one bike's BLE connection state, observed configuration,
command queue, retry policy, and foreground enforcement loop.

`BikeSettingsController` performs explicit repository transactions. It does not
mirror the whole database row in an independently writable signal.

### Signals rules

- Expose read-only signals from controllers; mutations happen through named
  commands.
- Use computed signals for derived state such as `canControl`, displayed config,
  effective enforced config, and primary recovery action.
- Use `batch` when one BLE frame updates multiple related signals.
- Dispose every stream subscription, effect, timer, and scan with its owning
  controller.
- Do not use application-global mutable signals.
- Do not write to SQLite from a widget build or a reactive computed callback.
- Do not use effects as an implicit command bus.
- An effect may bridge an external lifecycle into a controller only when its
  cleanup and write behavior are explicit and tested.
- Commands that can overlap expose pending state and are serialized or canceled
  deliberately.

## Persistence with Drift and SQLite

### Database location

Use `drift_flutter` to create `superduper.sqlite` in the application-documents
directory. This is the same directory that may contain the installed
`bikes.json` and `settings.json` files, but the filenames do not overlap.

Enable foreign keys. Use transactions for every operation spanning bike
metadata and preferences. Keep schema migrations in source control and test an
upgrade from every released schema version.

### Initial schema

#### `bikes`

| Column | Type | Rules |
| --- | --- | --- |
| `device_id` | Text | Primary key; non-empty BLE identity |
| `display_name` | Text | Non-empty |
| `region` | Text nullable | `us`, `eu`, or unknown until confirmed |
| `color_key` | Text | Stable palette key |
| `sort_order` | Integer | Stable Home ordering |
| `created_at_ms` | Integer | UTC epoch milliseconds |
| `updated_at_ms` | Integer | UTC epoch milliseconds |
| `last_connected_at_ms` | Integer nullable | Informational only |

#### `bike_preferences`

| Column | Type | Rules |
| --- | --- | --- |
| `device_id` | Text | Primary key and cascading foreign key to `bikes` |
| `desired_light` | Integer | SQLite boolean |
| `desired_mode` | Integer | 0 through 3 |
| `desired_assist` | Integer | 0 through 4 |
| `keep_light` | Integer | SQLite boolean |
| `keep_mode` | Integer | SQLite boolean |
| `keep_assist` | Integer | SQLite boolean |
| `background_requested` | Integer | Imported/user preference, Android only |
| `background_consent_version` | Integer | `0` until the V2 behavior is explicitly accepted |

#### `app_settings`

| Column | Type | Rules |
| --- | --- | --- |
| `singleton_id` | Integer | Always `1` |
| `active_bike_id` | Text nullable | Sole startup auto-connect target; foreign key to `bikes` with delete set null |
| `last_viewed_bike_id` | Text nullable | Informational foreign key with delete set null; never changes active status |
| `migration_notice_pending` | Integer | Whether an import result needs to be shown |

#### `data_imports`

| Column | Type | Rules |
| --- | --- | --- |
| `import_key` | Text | Primary key, initially `v1_json` |
| `outcome` | Text | `completed`, `no_source`, or `skipped_by_user` |
| `completed_at_ms` | Integer | UTC epoch milliseconds |
| `bikes_imported` | Integer | Count committed |
| `warnings_json` | Text | Local structured import warnings |

Database rows are persistence models. The repository maps them to immutable
domain types before exposing them to feature controllers.

### Persistence behavior

- Saving a newly confirmed bike inserts `bikes` and `bike_preferences` in one
  transaction.
- Saving the first bike also sets `active_bike_id` in that transaction.
- Making another bike active updates one `active_bike_id`; there is no per-bike
  boolean that could allow multiple active bikes.
- Forgetting the active bike promotes the remaining bike with the lowest
  `sort_order`, or clears `active_bike_id` when none remain.
- Repository initialization repairs a missing or invalid active reference by
  choosing the lowest `sort_order` in one transaction and recording a local
  warning.
- Renaming, region changes, color changes, desired-value changes, and lock
  changes are explicit repository commands.
- Forgetting a bike deletes it once; the foreign key removes its preferences.
- BLE reads never write observed state to SQLite automatically.
- Enabling `Keep this setting` saves the currently confirmed value as desired
  in the same transaction that enables the preference.
- A failed database write does not leave optimistic UI presented as saved.
- Background execution reads a versioned, stable representation of desired
  settings; it does not invent a second user-preference store.

## Installed user-data migration

### Goal

An app updated from version `0.7.8+58` must retain all valid saved bikes and
preferences found on the device. When imported bikes exist, the earliest bike
in saved order becomes active unless an existing V2 active choice already
exists. A fresh install must complete startup without creating fake migration
data.

The import runs before Home observes the database. It is local, transactional,
idempotent, and non-destructive.

### Source discovery

Look in `getApplicationDocumentsDirectory()` for:

- `bikes.json`
- `settings.json`

Do not search unrelated directories. Do not upload or expose their contents.
Do not delete, truncate, rename, or rewrite either file.

If a `data_imports` row already exists for `v1_json`, normal startup does not
import again. A recovery action may explicitly retry an outcome of
`skipped_by_user`.

### Installed bike representation

Each entry in `bikes.json` may contain:

| JSON field | Required representation | Default when absent |
| --- | --- | --- |
| `id` | Non-empty string | No default; invalid record |
| `name` | String | Regenerate if absent or empty |
| `region` | `200`, `201`, or `null` | Unknown |
| `light` | Boolean | No default; invalid record |
| `mode` | Integer 0 through 3 | No default; invalid record |
| `assist` | Integer 0 through 4 | No default; invalid record |
| `lightLocked` | Boolean | `false` |
| `modeLocked` | Boolean | `false` |
| `assistLocked` | Boolean | `false` |
| `modeLock` | Boolean | `false` |
| `color` | Integer palette index | `0` |

Region mapping is:

- `200` to `us`.
- `201` to `eu`.
- `null` to unknown.

For defensive import, string values `US`, `us`, `EU`, and `eu` may also be
accepted. Any other region becomes unknown and produces a warning.

`settings.json` may contain `currentBike`. That value represented transient
navigation rather than a durable auto-connect choice, so import it as
`last_viewed_bike_id` only when it matches an imported or already-existing bike.
It does not override active-bike selection.

The installed format has no durable active-bike field. After importing, set
`active_bike_id` to the valid bike with the lowest `sort_order` when V2 does not
already have an active bike. This implements the rule that the first configured
bike is active by default.

### Color migration

Freeze the installed palette index mapping in the importer and test every
index. V2 stores the resulting key:

```text

 1 ocean_mirage        9 peach_cream        17 frosted_mint      25 vanilla_latte
 2 sunset_blaze       10 emerald_wave       18 deep_space        26 pure_white
 3 electric_meadow    11 pastel_dream       19 silver_mist       27 dark_mode
 4 berry_pop          12 lavender_haze      20 stormy_gray       28 neon_cyber
 5 cotton_candy       13 mint_magic         21 midnight_ocean    29 synthwave
 6 mystic_twilight    14 bubblegum          22 sun_kissed        30 pixel_blue
 7 aqua_fresh         15 sky_breeze         23 ice_drop          31 midnight_sky
```

An absent, negative, or unknown index maps to `royal_horizon` and records a
warning. Palette display names may evolve; these persistence keys remain stable.

### Import algorithm

1. Open the SQLite database and finish its schema migration.
2. Query `data_imports` for `v1_json`.
3. If a terminal import outcome exists, continue normal startup.
4. Check the two exact JSON paths.
5. If neither file exists, transactionally insert a `no_source` import row and
   continue.
6. Read available source files without changing them.
7. Decode `bikes.json` as a top-level list and `settings.json` as a top-level
   object.
8. Validate and normalize each bike independently.
9. If a non-empty source list contains no valid bike, stop before opening the
   import transaction and show Migration Recovery. An intentionally empty list
   is a valid import.
10. Preserve the first occurrence's list position for `sort_order`. If the same
   device ID occurs again, the last valid record supplies the values and a
   duplicate warning is recorded.
11. Start one SQLite transaction.
12. Insert only bike IDs that are not already in the V2 database. Existing V2
    rows always win over installed JSON.
13. Insert the corresponding preferences for each inserted bike.
14. Preserve an existing valid V2 `active_bike_id`. Otherwise, set it to the
    valid bike with the lowest `sort_order`, including an already-existing bike
    when applicable.
15. Import a valid `currentBike` as `last_viewed_bike_id` without changing the
    active bike.
16. Set every imported `background_consent_version` to `0`, even when
    `modeLock` was true.
17. Insert the `completed` import row, counts, and warnings in the same
    transaction.
18. Commit.
19. Query the committed rows and publish the startup-ready state.
20. If warnings occurred, set `migration_notice_pending` and show a concise
    local summary after Home loads.

The importer itself starts no background service or BLE connection. After a
successful commit and Home initialization, normal foreground startup observes
the imported active bike and begins its automatic ride-setup session.

### Invalid-data policy

- A missing source file is not an error if the other source can be imported.
- An unreadable or syntactically invalid `settings.json` produces a warning but
  does not prevent valid bikes from importing.
- A syntactically invalid or non-list `bikes.json` is a recoverable startup
  failure because silently presenting an empty library could hide user data.
- A bike with an invalid required field is skipped while other valid bikes are
  imported.
- Unknown optional values use documented safe defaults and produce warnings.
- If source data exists but zero bike records are importable, show Migration
  Recovery before Home.
- Never clamp an invalid mode or assist into a different valid value. Skip the
  record and report the field.
- Logs and UI identify records by redacted suffix or list position, not by
  printing complete device identifiers in release builds.

Migration Recovery offers:

- `Retry import`.
- `Continue without imported bikes` with an explicit warning that source files
  will remain available.
- A local details view containing sanitized errors.

Choosing to continue writes `skipped_by_user`, preserves both JSON files, and
allows a future retry from app support/settings.

### Rollback and recovery

- The source JSON files remain untouched for the lifetime of V2 unless a future
  release introduces a separately reviewed cleanup policy.
- V2 never writes new state back into those files.
- A failed import transaction leaves no bikes and no `completed` marker in
  SQLite, so retry starts from a known state.
- If the database cannot open after a successful import, recovery operates on a
  copy or newly created database and leaves both the database file and JSON
  sources available for diagnosis.
- Reinstalling or clearing app data remains destructive because the operating
  system removes the application-documents directory; the app must not imply
  otherwise.
- An application rollback can still read the retained installed JSON snapshot,
  although changes made only in V2 will not be visible to the earlier version.

### Migration tests

## BLE subsystem

### Pure protocol codec

`BikeProtocol` is pure Dart and has no Flutter, plugin, database, or Signals
dependency. It owns:

- GATT UUID constants used by active behavior.
- Register selection payload `[3, 0]`.
- Validation and decoding of state frames.
- Encoding of complete ten-byte configuration writes.
- US wire modes 0 through 3.
- EU wire modes 4 through 7.
- Light, Mode, and Assist range validation.
- Typed protocol failures for short, malformed, and unsupported frames.

The state read contract remains:

- Assist at response byte 2.
- Light at response byte 4.
- Mode at response byte 5.

The write contract remains:

```text
[0, 0xD1, light, assist, wireMode, 0, 0, 0, 0, 0]
```

All codec behavior is test-first and does not require a bike.

### Transport adapter

`BikeTransport` defines SuperDuper's required operations without exposing
Flutter Blue Plus types to the rest of the app:

- Observe adapter state.
- Scan with supported advertisement filters.
- Stop scanning.
- Connect to one device.
- Observe connection state.
- Discover and validate required services.
- Read and write characteristics.
- Disconnect and dispose.

The Flutter Blue Plus implementation translates plugin errors into typed domain
failures and always cleans up subscriptions.

### Session state machine

Use sealed states with exhaustive handling:

```text
idle
  → connecting
  → discovering
  → connected
  → synchronizing
  → ready
  → reconnecting
  → disconnected
  → failed
  → disposed
```

Transitions are event-driven and testable. `connected` means the GATT transport
is available; `ready` means the initial state is known and every locked setting
has been confirmed. A disposed session rejects new commands. Selecting a
different bike disposes the current session before the next connection begins.

### Command scheduling

- One queue serializes all GATT operations for a bike.
- A read never overlaps a write.
- Repeated user changes may coalesce before transmission, but the final desired
  complete configuration is never lost.
- A command has a timeout and a typed result.
- Direct user commands take priority over periodic confirmation reads.
- Active-bike startup synchronization begins immediately after connection and
  service validation; it does not wait for the control route or a periodic
  timer.
- A successful write is followed by a confirmation read.
- A failed command does not update confirmed observed state.
- Reconnection uses bounded backoff and exposes the next retry action to UI.
- Returning to the foreground resynchronizes the active bike unless the user is
  deliberately using a temporary non-active session or manually paused
  reconnection.
- App lifecycle changes pause unnecessary polling when foreground execution is
  unavailable.

Poll timing is an implementation parameter, not product state. Start with an
immediate read on connection and a non-overlapping foreground interval, then
tune using real-bike traces.

### Enforcement algorithm

After a validated read:

1. Batch-update observed Light, Mode, and Assist.
2. Load desired values and lock choices from the repository-backed signal.
3. Compute the effective configuration.
4. If no locked value differs, schedule no corrective write.
5. If any locked value differs, enqueue one complete configuration write.
6. Confirm with a read.
7. Surface repeated mismatch as an error instead of entering an infinite loop.

For the startup path, the coordinator marks the active bike `Ready to ride` only
after this algorithm completes and all locked values match. When there are no
locked settings, a validated initial read is sufficient. A connection alone is
never presented as ride-ready.

The algorithm must cap corrective retries per synchronization cycle and include
enough structured logging to diagnose bike firmware that rejects a value.

## Android background-enforcement experiment

### Product question

Can V2 reliably enforce selected settings when the app is backgrounded or the
screen is locked without misleading users, excessive battery use, fragile OEM
behavior, or Play policy risk?

The answer is not assumed to be yes.

### Architecture boundary

Define a `BackgroundEnforcement` interface with:

- Platform capability.
- Current runtime status.
- Explicit enable and disable commands.
- Permission/association requirements.
- A versioned desired-setting input.
- Typed startup, connection, policy, and runtime failures.

The rest of the app depends only on this interface. The unsupported
implementation reports capability honestly and never exposes an inert toggle.

### Android spike

Prototype the platform-recommended approaches against a real bike:

1. Companion Device Manager association and device-presence observation.
2. A native `CompanionDeviceService` for presence-bound work.
3. A `connectedDevice` foreground service started by explicit visible user
   action when companion-device behavior is insufficient.
4. Native GATT ownership or a proven dedicated Dart background isolate.

Do not use the Flutter UI isolate as the sole execution owner. A service that
only displays a notification does not satisfy the feature.

The spike must establish one owner for a BLE connection. If native Android owns
background GATT, foreground Flutter commands must coordinate with or delegate to
that owner rather than opening a competing connection.

If the native service needs database access, expose a stable, versioned,
read-only SQLite view for desired settings. The native component must not write
user preferences or maintain an independent canonical preference store.

### Test matrix

Test at minimum:

- Android 10, the configured minimum.
- Android 12 foreground-service restrictions.
- Android 14+ typed foreground-service requirements.
- Android 16 companion-device presence behavior.
- A current Pixel device.
- At least one OEM known for aggressive background process management.
- App visible with screen on.
- App backgrounded.
- Screen locked.
- App removed from recents.
- Process reclaimed by the OS.
- Explicit force-stop.
- Bike powered off and back on.
- Bike leaving and returning to BLE range.
- Bluetooth toggled off and back on.
- Phone reboot.
- Notification permission denied.
- Companion association revoked.
- Official bike app attempting a competing connection.

Record enforcement latency, reconnect success, service/notification state,
battery use, and failure recovery. Force-stop is expected to require the user to
open the app again and must be described that way.

### Ship gate

Background enforcement ships only when:

- The service performs real BLE synchronization independently of a mounted UI.
- The supported lifecycle states have repeatable hardware evidence.
- The behavior meets current Android and Google Play foreground-service rules.
- Enabling is explicit and disabling always stops ongoing work.
- The persistent notification accurately describes the work.
- Failure is visible and recoverable.
- Battery measurements are acceptable to the product owner.
- Automated platform tests cover service configuration and lifecycle entry
  points.
- User-facing copy states the actual limits, including force-stop behavior.

If the gate fails:

- Do not ship Background Lock in V2.
- Remove its runtime permissions, service, and inactive UI.
- Preserve the imported preference locally without activating it.
- Describe `Keep this setting` as foreground/active-session enforcement.
- Revisit only when the platform or bike protocol provides a more reliable
  mechanism.

iOS background enforcement is not part of the V2 release plan. It requires a
separate Core Bluetooth lifecycle design and acceptance matrix.

## Permissions, privacy, and platform cleanup

### Contextual permissions

- Ask for Bluetooth access inside Add Bike or while fulfilling an active/saved
  bike connection. Previously granted access needs no new prompt.
- On Android API 31+, request the nearby-device permissions actually required
  for scan/connect.
- On Android API 29 and 30, request location only where the OS BLE scan contract
  requires it.
- Do not request location on iOS for a Bluetooth-only workflow.
- Explain permanently denied state and provide an Open Settings action.
- Request notification or companion-device permissions only when the user
  explicitly enables proven background enforcement.

### Manifest cleanup

Remove declarations not required by a shipped feature, including:

- Advertising ID.
- Internet, because help URLs open in the system browser and core behavior has
  no network client.
- System alert window.
- Ignore battery optimization, unless the background experiment proves it is
  both necessary and appropriate.
- Foreground-service declarations when background enforcement does not ship.
- Unbounded location declarations on Android versions that use nearby-device
  permissions.

Retain only platform usage descriptions that match runtime requests.

### Logging

- No analytics or remote crash SDK is introduced.
- Release logs redact full BLE identifiers and payloads that could identify a
  bike.
- Debug builds may expose a local diagnostic view with connection transitions,
  GATT validation, command outcomes, and sanitized import results.
- Sharing diagnostics is always an explicit user action and is not required for
  normal recovery.

## Risks and mitigations

| Risk | Mitigation |
| --- | --- |
| Installed data is silently lost | Import before Home, use one transaction, preserve JSON, and show recovery when zero records are importable |
| Signals becomes hidden global state | Constructor ownership, read-only exposure, named commands, and mandatory disposal tests |
| Drift and Signals create two mutable sources | SQLite owns saved data; repository streams feed read-only signals |
| BLE commands race | One per-session queue, typed timeouts, and confirmation reads |
| UI shows desired state as confirmed | Separate observed, desired, pending, and effective signals |
| Reconnection writes stale values | Require a validated read before enforcement and cap corrective retries |
| Startup connects the wrong bike | Store one active ID, default deterministically, label it in Home, and test migration/switching |
| Connection looks ride-ready before locks apply | Derive readiness from confirmed synchronization, not transport connection |
| Forget Bike is undone by async work | Dispose and disconnect before transactionally deleting; reject post-disposal commands |
| Plugin details spread through the app | SuperDuper-owned transport and permission interfaces |
| Background feature remains unreliable | Independent experiment with a hard ship gate and honest fallback |
| Native background service competes with Flutter BLE | Define one GATT owner and explicit handoff/delegation protocol |
| Permissions exceed actual behavior | Contextual requests and manifest audit against shipped features |
| Palette changes alter existing bikes | Migrate index to stable color key and never persist list position again |
| SDK or dependency churn destabilizes the rewrite | Pin stable toolchain and update deliberately after green builds |

## Definition of V2 complete

V2 is complete when:

- The preserved foreground feature set is implemented through the simplified
  workflows.
- Opening the app automatically prepares the persisted active bike and reports
  `Ready to ride` only after its locked settings are confirmed.
- The first saved or imported bike becomes active by default, and the user can
  explicitly change the one active bike.
- Every valid installed bike and preference is imported or a visible recovery
  path is offered.
- The migration is idempotent, transactional, and leaves source JSON untouched.
- Signals state has explicit ownership and disposal.
- SQLite is the only canonical store for V2 bike data.
- BLE protocol behavior is pure, typed, and comprehensively tested.
- Connection, command, and enforcement behavior is serialized and recoverable.
- Android and iOS release builds pass their minimum-version matrices.
- Permissions and privacy disclosures match the shipped app.
- Background enforcement either passes its complete ship gate or is absent from
  the release UI and runtime permissions.
- The full formatting, analysis, unit, widget, integration, migration, build,
  and hardware acceptance checks pass.
- The product owner has reviewed the code and approved release.
